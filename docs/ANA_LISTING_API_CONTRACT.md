# Ana listing API contract

Implementation contract, 2026-09-09. Backend owner: codex-ana-backend. All paths are backend paths; web owns forwarding through `/api/backend`. JSON errors use `{ok:false,error:string}`. No production verification is implied.

- `GET /api/listings`: public published listings only; optional `search`, `sellerCompanyId`, `statusCode` cannot expose nonpublic records. Returns `{ok:true,listings: Listing[]}`.
- `GET /api/listings/:idOrSlug`: public published detail; unknown/unavailable is 404. Returns `{ok:true,listing}`.
- `GET /api/listings?scope=owned` and `GET /api/listings/:idOrSlug?scope=owned`: bearer required; active company only (admin may supply sellerCompanyId). Includes drafts and closed records.
- `POST /api/listings`: bearer seller company member required, returns 201 and full listing. `PATCH /api/listings/:id` returns full listing, omitted fields unchanged, nullable fields accept null to clear. `DELETE` soft closes, preserving data.
- Sellers may set `draft`, `pending_review`, `paused`, `closed`; only admin may publish. Editing published content returns it to pending_review. Submission requires SDS already uploaded: create draft, upload documents, then PATCH status pending_review.

Listing write fields: `sellerCompanyId`, `locationId`, `title`, `materialTypeCode`, `quantity`, `quantityUnit`, `minimumOrderQuantity`, `pricePerUnit`, `currencyCode`, `listingStatusCode`, `carbonIntensityKgCo2e`, `description`, plus `specifications` below. Company/location and explicit materialTypeCode required on create; title required. Draft quantities/price may be null; submitted records require quantity > 0, MOQ > 0 and <= quantity, price >= 0, explicit currency and unit. Recorded zero is real zero, missing is null. Units supported: `ton` (metric tonne), `tonne`, `kg`, `lb`, `unit`; no automatic conversion. Slug is generated and stable.

`specifications` object (optional strings are nullable): `category`, `material`, `listingType`, `grade`, `color`, `shelfLife`, `storage`, `packaging`, `weight`, `usage`, `origin`, `quality`, `composition`, `frequency`, `state`, `availabilityFrom` (YYYY-MM-DD), `availabilityTo`, `sustainabilityNotes`, `originLocation`, `sameAsCompany` (boolean), `claims` (string[]), `additionalSpecs` ({label:string,value:string}[]). PATCH specifications replaces the entire object; send the full form. Empty/missing values are not fabricated. `materialTypeCode=other` supports Others.

Listing responses include all write fields, `id` (number), `slug`, `sellerCompanyName`, `sellerVerificationStatusCode`, `sellerVerified` (true only for verified account status), `location` ({id,name,addressLine1,addressLine2,city,stateProvince,postalCode,countryCode,latitude,longitude}), and `documents` below. Company identity and verification are server-derived. Price is recorded public pricing under existing product behavior; membership policy change requires a separate decision.

Files: `POST /api/listing-documents` with bearer and JSON `{listingId,documentTypeCode,fileName,contentType,contentBase64}`. Types: `photo` (PNG/JPEG/WebP), `sds` (PDF), `certificate` (PDF). Maximum decoded 5 MiB per file. Actual bytes persist in SQL with SHA-256; remote/data/blob URLs are not accepted. Response 201 `{ok:true,document}` with `id,listingId,documentTypeCode,fileName,contentType,byteLength,sha256,fileUrl,verificationStatusCode`. `fileUrl` is relative `/api/listing-documents/:id/download`; web proxy must forward binary response and authorization for owner drafts. Public downloads only for published listings. `GET /api/listing-documents?listingId=:id[&scope=owned]` applies identical visibility rules; listingId required. `DELETE /api/listing-documents/:id` soft deletes, owner/admin only. Removing reviewed content returns published/pending listings to pending_review while an SDS remains; removing the last SDS returns them to draft. Listing updates and document mutations serialize on the listing row, preventing approval from racing an SDS removal. Download returns actual bytes and safe content-disposition. No fabricated SDS links or verified certifications.

Onboarding: existing `POST /api/onboarding` additionally accepts `feedstockInterests: string[]`, `otherFeedstockInterest: string|null`, `industry`, `jobTitle`, `website`; choosing `Others` requires the description. These persist with company onboarding preferences. `GET /api/onboarding` returns `{ok:true,onboarding:{companyId,industry,jobTitle,website,feedstockInterests,otherFeedstockInterest}}` for active company. POST retains existing `{ok,onboarding,user}` response. Free completion remains payment independent; concurrent retries serialize per user and reuse owned company, never promote an existing non-owner membership.

Facilities: authenticated `GET /api/locations` returns `{ok:true,locations:[{id,companyId,locationTypeCode,name,addressLine1,addressLine2,city,stateProvince,postalCode,countryCode,latitude,longitude,isDefault}]}` scoped to active company. Optional `companyId` must match active company unless admin. Existing `POST /api/locations` creates owned facilities using these fields. Use numeric `locationId` from this response when saving listings. Do not use synthetic facility IDs from browser session fallbacks.

The canonical shared types are exported from `@eco-globe/shared` in `packages/shared/src/listing-api.ts`. Document response certification code is `certification`; both `certificate` and `certification` are accepted on upload. Request bodies are bounded to 8 MiB before JSON parsing.


Legacy document boundary: existing FileUrl-only rows are preserved unchanged in SQL but excluded from the new document responses/downloads because no owned file bytes exist for them. Sellers must deliberately re-upload those files; this migration does not fetch external URLs or fabricate working attachments. Existing company sessions whose active-company membership has been removed/inactivated now return 401 intentionally. An explicitly empty onboarding preference clears it; omitted fields preserve it, and the frontend preloads existing preferences before saving.
